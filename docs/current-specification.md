# System Engineer Simulator Platform 現行仕様書

## 1. 文書の目的

本書は、M365 Copilotへ本プロジェクトの現行仕様・構成・制約を説明し、今後の調査や改善依頼の前提として共有するための資料です。

- 本書は**現時点で実装されている仕様**を記載します。将来構想や未実装機能は現行機能として扱いません。
- 他案件へ展開する際の理念・設計ルールは[共通ルール](./simulator-rules.md)を参照してください。
- 実装と本書に差異がある場合は、ソースコードとシナリオJSONを正とします。
- このアプリは教育用の疑似環境です。実サーバー、実クラウド、Microsoft 365、Oracleには接続しません。

## 2. システム概要

本リポジトリは、案件共通の学習ロジックを共有パッケージとして段階的に整備し、InfrastructureとDevelopmentの案件シミュレーターを提供するnpm workspaces Monorepoです。各アプリは独立したReact SPAです。

| 項目 | 現行仕様 |
|---|---|
| アプリケーション | React + TypeScript + Vite、npm workspaces |
| 主な表示 | Windows風デスクトップ、シミュレーション作業画面、案件デスク |
| Infrastructure案件定義 | `apps/infrastructure-project-simulator/src/data/scenarios/*.json` |
| Development案件定義 | `apps/development-project-simulator/src/scenario.ts`（現段階では固定のプロトタイプ） |
| 共通パッケージ | `packages/` 配下の7 workspace |
| 状態保存 | ブラウザーの`localStorage`。シミュレーション保存形式はversion 2 |
| 外部接続 | なし。操作・コマンド・クラウド・助言はアプリ内の疑似処理 |
| シナリオ検証 | Zodによる構造・参照・一部の整合性検証 |

### Monorepoアプリ

- **Infrastructure Project Simulator** — 既存のWindows Server移行シミュレーター。既存の学習モードと案件機能を維持します。
- **Development Project Simulator** — EC商品検索案件で、顧客要望・関係者ヒアリング・API連携・性能調査・セキュリティ・QA・運用資料を読み、要件定義から運用引継ぎまで12の判断を進めます。回答後は利点・残リスク・選択後の影響・次工程への引継ぎを表示します。「実装」工程もコード編集ではなく、実務上の判断を選ぶ演習です。シナリオ定義は現在`scenario.ts`に固定され、外部案件JSONの追加には未対応です。
- **共有パッケージ** — 共通の状態・イベント・SEスキル、Story/Case Study型、案件デスク型、助言境界、学習資産、採点補助を提供します。既存Infrastructure UIやドメイン全体の共通化は未完了です。

### 学習対象

- 対象は経験0〜10年の新人〜中堅SE。専任プログラマ向けの言語・ライブラリ入門や資格対策は対象外。
- 共通目標は、初めての案件で確認対象・調査方法・相談先・判断根拠を選び、説明・エスカレーション・振り返りまで行えること。
- APサーバー、DBサーバー、Oracle、JDBC、Resin、Java
- DNS、TTL、証明書・秘密鍵、Windowsサービス、タスクスケジューラ
- 現行調査、構成把握、資料確認、データ移行、疎通確認
- 利用者周知、工数見積、会議・議事録、Go/No-Go、切戻し、障害調査

## 3. 利用者の基本フロー

1. 案件、基盤、接続先、学習モードを選択する。
2. 必要に応じてクラウド風の疑似基盤を構築する。
3. シミュレーション画面で現行環境を調査し、新環境へ移行する。
4. 案件デスクで資料・関係者・計画・切替判断を扱う。
5. 操作イベント、移行結果、計画内容をもとに監査レポートを確認する。

シミュレーション作業画面では現行・移行先を並べて表示し、接続先やツールを独立して操作できます。コマンド出力と管理ツールの状態はシナリオに基づく疑似結果です。

## 4. 学習モード

プロダクト上の学習層は、Observation（全体理解）、Case Study（条件依存判断）、Playbook（未経験案件の確認支援）の3層です。現行UIの名称とは段階的に対応させ、Observationを問題集の短縮版、Playbookを正解集として扱わない方針です。

### 4.1 チュートリアル

AI上司役の案内に従い、調査・移行操作を行います。実行イベントに対応した手順と解説が表示されます。

### 4.2 初級

調査目的を示し、実行方法は利用者が探します。実行後に解説を確認できます。

### 4.3 中級

更改目標と調査範囲を示します。確認順やコマンド例は原則表示せず、自分で調査・構成整理・計画を進めます。

### 4.4 上級

「切替後にログインできない」など、障害の症状を起点に原因を調査します。

### 4.5 エキスパート

シナリオで定義された障害を選んで移行済み環境に発生させ、症状やログから原因特定・復旧を試みます。

### 4.6 観察モード

- シナリオJSONの`storyMode`で有効化されている場合に利用できます。
- 現行シナリオでは33手順。現行調査、移行計画、構築、移行、切替、確認の工程を表示します。
- 実際の画面をスポットライト表示し、疑似コマンドと出力、操作結果、解説を見せます。
- 手順によりクイズ、誤答時の失敗体験、失敗分岐、スキップ、自動再生を提供します。
- 観察専用のプレビューであり、通常の作業状態・監査イベント・セーブデータを更新しません。
- 完了時に案件の流れと学習内容を振り返り、チュートリアルへ移る導線があります。

### 4.7 問題集モード

- 問題集は通常の移行セーブデータとは別の画面で動作します。
- 10カテゴリ（DNS、Active Directory、Oracle、Data Pump、JDBC、利用者周知、Go/No-Go、切戻し、証明書、バッチ）を扱います。
- 20の案件テーマに初級・標準・上級の固定条件を用意し、合計60エントリーを出題順シャッフルして提示します。
- 1エントリーにつき現在は1問です。案件条件と設問・選択肢を同じ画面に表示します。
- 選択後に、適合度、利点・コスト、条件、解説、選択肢比較、必要に応じて失敗シミュレーションを表示します。
- 適合度は案件・難易度ごとに事前定義された0〜3点です。難易度別・判断領域別の成績を表示します。
- 判断理由の記述と重視した条件の選択は任意です。現行の適合度スコアには反映されず、記入有無のみを振り返りに表示します。
- 出題順はシャッフルしますが、毎回新しい条件を生成する仕組みではありません。
- 「初級・標準・上級」はシナリオ背景や設問も異なりますが、問題形式と進行は共通の単一選択式です。

### 4.8 Development Case Study

- `apps/development-project-simulator`はLayer 2のCase Studyとして動作し、対象を経験0〜10年の新人〜中堅SEと定義します。
- EC商品検索案件を12判断で扱い、顧客要望、関係者メモ、API、データ性能、セキュリティ、QA、運用資料を工程ごとに提示します。
- 判断前に重点となる案件事実、判断理由、相談・承認先を入力します。事実のうちシナリオが重点とする材料を何件選んだかは透明な規則で表示します。
- 自由記述は生成AIが理解したり自動採点したりせず、判断理由の証跡として保存・振り返り表示します。
- 回答後は選択肢の利点・残存リスク・結果、相談ポイント、次工程への引継ぎを表示し、前工程へ戻っても選択・理由・相談先を保持します。
- 完了時に工程全体、スキル別適合度、各判断の根拠・理由・相談先を振り返ります。ブラウザー再読み込みをまたぐ保存は現時点で実装していません。
- サイドバーのプレイブックはLayer 3の確認質問、成果物、レビュー観点、リスクを参照する補助機能です。正解一覧やCase Studyの代替モードではありません。

## 5. シミュレーション対象と操作

### 5.1 ドメインモデル

サーバー、VM、Database、DNS、Service、Task、Certificate、Configuration Fileを型で表現します。ランタイム状態にはソフトウェア、サービス状態、タスク、証明書、設定ファイル、DBバージョン・スキーマ・データ世代・役割などを持ちます。

### 5.2 疑似コマンド・管理ツール

シナリオと現在状態に応じ、次のようなコマンドや疑似管理ツールを使います。

- コマンド例: `systeminfo`、`ipconfig /all`、`hostname`、`netstat`、`route print`、`nslookup`、`java -version`、`lsnrctl status`、`curl`
- Windows風ツール: サービス、タスクスケジューラ、イベントビューアー、証明書、DNS、設定ファイル、データベース等
- 移行操作: ミドルウェア導入、サービス・タスク・証明書・設定・JDBCの移行、DB移行、DNS変更、起動・停止・検証

コマンド名や操作は学習用に再現したものであり、実際のWindowsやOracleの全機能・仕様を実行するものではありません。

### 5.3 DB移行方式

案件デスクでData Pump、RMAN、Data Guardのいずれかを選びます。シミュレーションはスキーマ、同期状態、データ世代などで方式の差を表し、方式に応じた疑似操作や監査結果に反映します。実際のOracleデータ、バックアップファイル、転送量、製品コマンドの完全な動作は再現しません。

### 5.4 AWS / Azure

AWS・Azure風の画面でVPC/ネットワーク、サブネット、セキュリティグループ/ファイアウォール、VM等を操作できます。設定はアプリ内だけに保存され、実クラウドリソースは作成しません。

## 6. 案件デスク

案件デスクは技術作業と並行して、案件管理情報を記録する画面です。

| タブ | 現行機能 |
|---|---|
| 案件概要 | 利用者数、停止可能時間帯、許容停止時間、重要度などを確認 |
| 調査・構成 | 調査ノートを記録し、構成要素間の依存関係を登録 |
| 案件資料・判断根拠 | 設計書等を読み、資料の節を引用して判断と理由を記録 |
| メール | シナリオ定義の受信メールを確認。重要メールの未読状態は評価対象 |
| Teams | 関係者発言に返信候補を選択。回答は案件状態に記録 |
| 会議・議事録 | 議題の判断を記録し、計画との整合性を評価 |
| 工数見積 | 資料を根拠として作業前に人時を見積もり、実行済み作業のモデル工数と比較 |
| 計画・周知 | 停止時間、TTLリード日数、周知、DB方式、切戻し計画を記録 |
| 切替判断 | Go/No-Go、継続、切戻し等の判断を記録し、切替準備項目を確認 |

メール・Teams・周知はアプリ内の演習です。実際のメール送信やTeams通信はしません。工数は実時間計測ではなく教材用モデルです。

## 7. 切替準備と監査・評価

- 切替準備チェックは、移行先APの直接疎通、選択DB方式の移行・同期、TTL計画・事前適用、利用者周知、停止時間、切戻し、会議合意、未解決事項などを確認します。
- 未完了項目は利用者へ示されますが、すべてのGo判断や操作を一律に強制ブロックするわけではありません。
- 最終監査レポートは、シナリオ定義の監査チェック、必要イベント、推奨順、プロジェクトデスクの記録、障害件数等をもとに結果を算出します。
- プロジェクト品質、移行成功率、停止時間、障害対応、運用品質等を評価します。未実施項目・順序の警告・改善案も表示します。
- 評価の一部はシナリオ別のイベント・キーワード・モデル工数に基づくローカル規則です。自然言語の妥当性を生成AIが理解・採点するものではありません。

## 8. シナリオJSON

### 8.1 読み込み

`apps/infrastructure-project-simulator/src/data/scenarios/*.json`をInfrastructureアプリ起動時に読み込みます。シナリオはZodスキーマで検証されます。現在の構造は[`models.ts`](../apps/infrastructure-project-simulator/src/domain/models.ts)と[`scenario.ts`](../apps/infrastructure-project-simulator/src/domain/scenario.ts)を参照してください。Development案件は現時点で[`scenario.ts`](../apps/development-project-simulator/src/scenario.ts)へ固定定義されています。

### 8.2 主な定義項目

- 基本情報: `id`、`title`、`description`
- 案件条件: `project`（利用者数、許容停止時間、停止枠、重要度、構成要素、依存関係）
- 案件運営: `projectDocuments`、`decisionReviews`、`projectMails`、`projectChats`、`projectMeetings`、`projectEffortPackages`
- 資産: `assets.servers`、`vms`、`databases`、`dns`、`services`、`tasks`、`certificates`、`configurationFiles`
- 疑似環境: `commands`、`incidents`、`learningObjectives`、`learningOrderByMode`
- 学習: `tutorialSteps`、任意の`storyMode`
- 評価: `auditChecks`、`recommendedOrder`、`advisorContext`

### 8.3 参照・拡張上の注意

- JSONを追加すると案件選択へ読み込まれますが、現行シミュレーターは移行元・移行先のAPサーバーとDBサーバーを前提にしています。任意種別の業務シミュレーターをJSONだけで追加できる汎用エンジンではありません。
- VMとホスト、DBとDBサーバー、DNS AレコードとサーバーIP、資料とメール/判断等の参照整合性を検証します。
- 操作イベント名、学習順、監査チェック、推奨順序はUI・進行判定と連動します。新しいシナリオではJSONだけでなく、必要に応じてドメインロジックやテストも更新します。
- 観察モードは`tutorialSteps`の手順IDと`storyMode.steps[].tutorialStepId`を対応させます。クイズや自動操作の内容もシナリオ側で定義します。

## 9. 保存、助言、外部サービス

- 通常のシミュレーション状態はブラウザーの`localStorage`に保存され、保存形式はversion 2です。読み込み時にZodで検証し、形式不正時はエラーを表示します。
- 保存対象には実行環境、DNS、コマンド履歴、移行パッケージ、監査イベント、案件デスク、クラウド風疑似状態等が含まれます。
- 観察モードは通常のセーブデータを変更しません。問題集モードの回答状態は現在の画面内で管理され、通常のシミュレーション保存形式には含まれません。
- 助言は`Advisor`インターフェースを通じて差し替え可能です。標準実装はコマンド結果・仮説・接続サーバー等を使うローカルルールベースです。
- 現行実装はMicrosoft 365 Copilot、外部生成AI、メール、Teams、実サーバー、AWS、Azureに問い合わせません。M365 Copilotは本書を仕様理解の入力資料として利用するだけで、アプリとの連携機能はありません。

## 10. 現行の制約・既知の改善余地

1. 問題集の条件は固定定義で、ランダムに数値・制約を生成する機能はありません。ランダム化されるのは出題順です。
2. 問題集は各案件1問の選択式です。実案件のような段階的な調査、複数の判断、関係者との合意形成を1ケース内で連続して行う形式ではありません。
3. 問題集の適合度は事前定義値です。選択理由・引用資料・根拠の品質は、問題集の適合度スコアに反映されません。
4. 難易度は条件・背景・設問の差を持ちますが、問題形式や手順数による体系的な段階設計は限定的です。
5. 障害や製品動作は教育用の抽象化です。実環境での作業手順・性能・ライセンス・製品バージョンの正確性を保証するものではありません。
6. 標準アドバイザーや評価の一部はルール・キーワード照合であり、AIによる自由な案件レビューではありません。

- テスト: `npm test`
- 型チェックと本番ビルド: `npm run build`

- テストは主にドメインロジックとシナリオ検証を対象としています。コンポーネントの包括的なUI自動テストは現状確認できていません。
