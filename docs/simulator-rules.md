# System Engineer Project Simulator 共通ルール

## 1. 目的と適用範囲

この文書は、Windows Server移行以外のシステム開発・運用案件にも展開する際に守る、シミュレーターの理念、学習設計、拡張設計、シナリオ作成のルールです。

- 本書は将来の拡張に対する**設計ルール**です。現在のコードがすべてのルールを実装済みという意味ではありません。
- 現在の実装機能は[現行仕様書](./current-specification.md)を参照してください。
- コード変更時は既存のWindows Server移行シナリオと学習体験を維持し、汎用化のための変更と既存仕様の変更を区別してください。
- 現在はnpm workspaces MonorepoにInfrastructureアプリ、Development判断演習プロトタイプ、および共通型・補助ロジックの初期パッケージが存在します。共通パッケージ化済みの範囲を超えて、両アプリの画面やドメイン全体が統合済みだと説明しないでください。

## 2. シミュレーターの理念

### 2.1 学ぶ対象は製品名ではなく、案件の進め方と判断

シミュレーターの中心価値は、特定のOS、DB、クラウド、プログラミング言語を操作することだけではありません。利用者がSEとして、事実を集め、根拠を整理し、関係者と合意し、リスクを引き受ける判断を行い、その結果を確認・報告する経験を安全に得ることです。

### 2.2 共通の学習ループ

案件に応じて工程の順序や反復を変えられるようにしつつ、次の学習要素を共通の構成要素として扱います。

1. **案件を理解する** — 目的、利用者、制約、成功条件を把握する。
2. **調査する** — 現状、資料、ログ、依存関係、不明点を確認する。
3. **判断・計画する** — 選択肢、根拠、コスト、リスク、担当、期限を整理する。
4. **調整・合意する** — 顧客、利用者、開発、運用など、必要な関係者と決定を記録する。
5. **実施する** — 案件ドメインに応じた作業を行う。
6. **確認する** — 期待した状態・受入条件・証跡を照合する。
7. **問題に対応する** — 事実から原因を絞り、影響抑止、継続、延期、切戻し等を判断する。
8. **報告・振り返りをする** — 結果、未解決リスク、改善点を説明する。

これは固定手順ではありません。複数工程が並行したり、調査・計画・実施を反復したりする案件を許容してください。特定の作業順をすべての案件の唯一の正解にしないでください。

## 3. 共通機能と案件ドメインを分ける

新しい案件を追加するときは、「案件共通の機能」と「その案件で扱う専門領域」を混在させないでください。

### 3.1 共通コアに置く機能

- 案件概要、学習モード、進行・状態管理
- 調査記録、資料・判断根拠、関係者との会話、会議・議事録
- 工数・計画・周知・承認・切替判断等の共通ワークフロー
- 操作イベント、監査・評価、フィードバック、振り返り
- セーブデータ、シナリオ読み込み・検証、共通の画面枠組み
- 助言インターフェースなど、実装差し替え可能な境界

### 3.2 案件ドメイン側に置く機能

- 案件で扱う資産・成果物・関係者・依存関係
- 調査方法、操作アクション、状態遷移、ログ・出力
- 受入条件、障害・失敗分岐、復旧方法
- 専門用語、案件固有の選択肢、評価基準
- 工程、役割、作業イベントなどの案件固有情報

新しいドメインの都合で共通コアの全画面に条件分岐を足し続けないでください。共通の概念とドメイン固有の概念を明示し、差し替え可能な定義・アダプター・モジュールとして設計してください。

## 4. 汎用化に関する実装ルール

1. **ドメインを列挙型へ直書きし続けない。** 新規ドメインを加えるたびに`AssetRole`、ツール一覧、イベント判定、保存形式、UIの多数の固定分岐を同時に改変する設計は避ける。
2. **共通ライフサイクルと専門作業を分ける。** 案件管理・資料・根拠・会議・評価は共通化し、サーバー操作、Web機能開発、モバイル配布等の実行モデルはドメイン固有にする。
3. **シナリオをデータで記述する。** 案件名、制約、資料、会話、判断、成功条件、学習コンテンツなど、変更頻度の高い内容はシナリオ側で定義する。汎用ロジックを特定シナリオのIDや文章に依存させない。
4. **JSONだけで拡張できる範囲を正確に示す。** 新しい業務が新しい資産モデル・アクション・状態遷移を必要とする場合、データ追加だけで動くと説明しない。ドメイン実装やUIアダプターが必要な境界を明記する。
5. **既存シナリオとの後方互換性を守る。** 省略可能フィールドには妥当な初期値を設け、保存形式変更にはバージョン管理・移行・不正データの明示的エラーを用意する。
6. **共通コアから特定ドメインの用語を排除する。** 「DNS TTL」「Oracle Listener」等の知識は移行ドメインのパッケージに置き、Web開発案件にも意味のない必須項目にしない。
7. **評価は設定・定義可能にする。** シナリオのイベント、受入条件、評価基準を使い、共通エンジンへ個別案件の採点文言を埋め込まない。

### 4.1 拡張の概念モデル

新ドメイン導入時は、少なくとも以下の境界を設計してください。名称や実装形式は既存コードとの整合を優先し、必要以上に抽象化しないこと。

| 境界 | 役割 |
|---|---|
| Project Scenario | 案件の目的、背景、利用者、制約、成功条件 |
| Domain Model | 案件固有の資産、成果物、関係者、依存関係 |
| Domain Actions | 調査・作業・検証など、学習者が実行できる操作 |
| Workflow Events | 事実として記録する操作結果・判断・合意 |
| Learning Content | 手順、観察アクション、説明、クイズ |
| Assessment Rules | 根拠、受入条件、トレードオフ、評価とフィードバック |
| Domain UI Adapter | 専門領域の状態や操作を共通画面枠へ接続する表示・操作境界 |

これらを必ず個別ファイルやクラスへ分割する必要はありません。既存のプロジェクト規模と実装に合う最小構造を選びます。

## 5. 教材・シナリオ作成ルール

### 5.1 案件情報

- 設問に答えるために必要な条件・資料・会話・ログを、回答前に学習者が確認できるようにする。
- 利用者数、停止可能時間、予算、期限、影響範囲、可用性、監査要件などは、設問や判断に実際に影響させる。飾りの数値を置かない。
- 不明情報は意図的な調査課題として使う。その場合は「不明」であることと、誰に何を確認するかが学べるようにする。
- 資料、メール、会議、作業計画、評価結果の間で矛盾を作る場合は意図を持たせ、調査・合意・リスク管理につなげる。

### 5.2 選択肢と判断

- 学習目標が判断力の場合、選択肢は明白な善悪だけで作らず、可能な限りそれぞれに利点・コスト・前提・残存リスクを持たせる。
- すべての選択肢を同等に正しいと見せる必要はない。安全性・影響・時間・費用などの条件から、より妥当な選択とその理由を説明する。
- 「何を選んだか」だけでなく、「どの事実を根拠にしたか」「何が未確認か」「誰と合意するか」を学ばせる。
- 理由や資料引用を評価するなら、入力を任意の飾りにせず、透明な評価基準とフィードバックに反映する。自動評価できない文章をAIが理解したかのように採点しない。
- 条件や未確定事項が異なれば、妥当な選択や採点も変わり得ることを示す。固定された唯一の正解ルートを暗記させない。

### 5.3 失敗・障害

- 失敗を表示するときは、判断・作業から影響に至る因果を示す。
- 回答に関係しない汎用障害を機械的に出さず、学習者の選択やシナリオ内の事実と整合させる。
- 影響、利用者、データ、サービス、期限など何が悪化するかを具体化する。
- 復旧・抑止・継続・延期・切戻し等の選択肢と、その前提や副作用も扱う。
- 実務上危険な操作を促す教材は、疑似環境・明確な警告・状態初期化などの安全策を設ける。

### 5.4 難易度と学習モード

- 観察・チュートリアル・実践・問題集等は、単に説明量を変えるだけでなく、学習者に求める行動を分ける。
- 初級では目的・確認対象を明瞭にし、標準では複数の条件・役割・合格条件を組み合わせ、上級では不確実性・相反する制約・時間制限・影響範囲を扱う。
- 難易度を名乗る各段階で、問題数・判断ステップ・証拠の量・前提知識・評価方法のどれが変わるかを明記する。
- 教材の難しさは情報量だけでなく、判断の構造で段階化する。正解の曖昧さだけで難しくしない。

## 6. 画面・操作のルール

- 学習に必要な案件条件と設問・作業対象を、判断時に同じ画面または容易に見比べられる位置へ表示する。
- 初学者向け操作では、操作対象、実行結果、意味、次に確認すべきことをつなげて示す。
- ハイライトや工程表示は現在の学習対象と一致させる。対象がない状態でステップを進めない。
- 破壊的・重要な判断は、影響と取り消し条件を事前に知らせる。確認画面が単なる飾りにならないよう操作結果へ反映する。
- エラー、保存失敗、対象不在、未解決条件を隠さず表示する。成功したように見える代替表示を行わない。
- 観察モード、問題集モード、実践モードの状態やセーブデータが意図せず混線しないようにする。

## 7. 評価・レビューのルール

- 得点はシナリオで提示した事実・選択・作業イベント・根拠に結び付ける。
- 評価理由を利用者が追跡できるよう、評価対象、配点、未達条件、改善方法を示す。
- 作業を実行しただけで無条件に加点せず、必要に応じて結果確認、証跡、承認、運用引継ぎも評価する。
- 工数や停止時間等のモデル値は、実計測値と誤認されない名称・説明にする。
- レビュー文は案件の具体的条件・選んだ案・残るコスト・不足情報を参照する。選択理由を読んでいないのに、理由を理解したように書かない。
- トレードオフが存在する場合は、最高点を「常に唯一の正解」と断定せず、評価基準と前提を開示する。

## 8. 安全性・実環境との境界

- 新しいコネクターを追加しない限り、シナリオ操作はローカルな疑似状態の範囲で完結させる。
- 実サーバー、クラウド、メール、Teams、外部AI等に接続する機能を追加する場合は、明示的な設定・権限・同意・資格情報管理・エラー処理・プライバシー説明を別途設計する。
- 教育用コマンド出力や製品挙動を、本番作業手順として保証しない。実環境との差と適用バージョンを明記する。
- ログ、資料、セーブデータに秘密情報や実利用者の個人情報を入れない。サンプルは架空データを使用する。

## 9. テスト・完了条件

新しいドメインやシナリオを追加する際は、少なくとも以下を確認します。

1. 既存の移行案件が引き続き読み込め、主要な既存モードで進行できる。
2. シナリオ内のID、依存関係、資料参照、操作イベント、評価条件が検証される。
3. 選択・操作による状態変化と、成功・失敗・復旧経路が期待どおりである。
4. 判断材料、理由、評価、フィードバックが整合し、表示文だけの疑似評価になっていない。
5. 保存・再読み込み・古い保存データの互換性・不正データのエラーを確認する。
6. 画面の重要なユーザーフローを可能な範囲で自動テストし、少なくとも手動確認の範囲と未確認事項を記録する。
7. 利用者に「何を学ぶか」「何が実機と異なるか」が明確である。

## 10. 推奨する横展開順

1. **Web業務システム開発案件**を最初の別ドメイン候補とする。要件整理、設計、実装計画、テスト、リリース、障害対応を題材にし、案件デスクの再利用性と技術作業の差し替え境界を検証する。
2. その検証を踏まえて、業務アプリ、モバイルアプリ、運用保守、PM等へ広げる。
3. ATM・決済等の高信頼性案件を扱う場合は、金融知識を表面的に簡略化せず、監査・安全・データ整合性・業務継続の専門家レビューを前提にする。

アルゴリズム演習や特定言語の文法練習など、主目的が個別コードの実装技能である教材は、本シミュレーターの案件判断中心の学習モデルと分けて検討してください。

## 11. 現行実装から汎用化する際の注意

現在の実装は設計理念の一部を備えていますが、まだ移行案件固有のモデルに依存しています。

- [`AssetRole`](../src/domain/models.ts)は`application`、`database`、`dns`に限定されています。
- [`Scenario`](../src/domain/scenario.ts)の検証は、現在の移行元・移行先APサーバーおよびDBサーバーを要求します。
- 画面・操作イベント・監査の一部は、Resin、Oracle、DNS等の移行作業を前提とします。
- 案件資料・会議・周知・根拠・切替レビュー等は再利用可能な共通要素の候補です。ただし、新ドメインに適合するかは実際のシナリオで検証してください。
- そのため、現段階で「JSONを追加するだけで任意のシステム開発案件を追加できる」とは言えません。別ドメインの追加では、共通コアとドメイン固有モデルの分離、既存シナリオの互換性維持、拡張箇所のテストが必要です。
