# Windows Server Migration Simulator

Windows Server更改を題材に、仮想デスクトップからRDP接続し、調査・移行・切替・障害対応を体験する日本語SPAです。実サーバーやAWS/Azureには接続せず、シナリオJSONの状態だけを操作します。

## Windowsで起動

対応するNode.js（20.19以降の20系、または22.12以降）をインストールし、エクスプローラーでリポジトリを開いて **`Start Simulator.bat`** をダブルクリックします。初回起動時に依存関係をインストールし、既定のブラウザーで開きます。終了時は起動したコンソールで `Ctrl+C` を押してください。

開発時の回帰テストは`npm test`、型チェックと本番ビルドは`npm run build`で実行します。

## はじめ方

起動するとWindows風デスクトップが表示されます。案件、オンプレミス/AWS/Azure、難易度を選び、デスクトップのCMD・PowerShell・エクスプローラー・管理ツールから接続アプリを選択してRDP接続します。AWSはEC2風、Azureは仮想マシン風の画面ですが、表示・接続はすべてシミュレーションです。

AWSを選択した場合は、コンソールの「ネットワーク」でVPCと、その範囲内に移行先サーバーIPを含むサブネットを作成します。「セキュリティ」でセキュリティグループとTCP 3389 (RDP)、8080 (AP)、1521 (Oracle) の必要なインバウンドルールを設定し、「EC2」から移行先インスタンスを起動します。TCP 3389が許可されるまで移行先へのRDPはできず、8080/1521の不足は疎通テストや切替後のイベントログに反映されます。VPC・サブネット・EC2もアプリ内の疑似リソースであり、実AWSリソースは作成しません。

| モード | プレイヤーに表示する内容 |
|---|---|
| チュートリアル | AI上司役のガイドが次の調査を案内し、実行後に確認目的を説明 |
| 初級 | 調査目的のみ。実行方法は自分で発見し、確認後に解説 |
| 中級 | 更改目標と調査範囲のみ。確認順・コマンド例は表示せず、ローカル助言は要求時のみ |
| 上級 | 「切替後、ログインできません」の症状のみを提示 |
| エキスパート | 移行済み環境にシナリオ定義の障害を1件発生させ、症状だけを提示 |

操作はブラウザーの`localStorage`へ自動保存されます。デスクトップの「続きから始める」で再開し、実行中は「最初からやり直す」で初期化できます。version 2セーブは後から追加された項目の初期値を補って読み込み、再開前に入れ子の実行状態まで検証します。形式が壊れている場合はセーブエラーを表示し、続行しません。

中級・上級・エキスパートでは「ローカル助言を依頼」から、接続中サーバー・直近のコマンド結果・未検証の仮説に基づく調査のヒントを取得できます。助言は`Advisor`インターフェースのローカル実装で生成され、外部サービスへ送信されません。別の助言実装は`App`へアダプターを渡して差し替えられます。

## 調査・操作

旧・新サーバーを左右に並べ、接続先や同じツールを独立して切り替えて比較できます。初期画面には構成の答えを表示せず、コマンドや疑似Windows管理ツールから調査します。

```text
hostname
systeminfo
ipconfig /all
netstat -ano
route print
nslookup intra.example.local
java -version
services.msc
taskschd.msc
eventvwr.msc
certlm.msc
notepad resin.conf
type jdbc.properties
```

- **services.msc** — サービス状態、起動種類、実行ユーザーの確認と起動・停止。
- **services.msc** — サービスの起動・停止に加え、起動種類を「自動 / 手動」に変更できます。新APではResinを自動起動に設定し、起動後の状態を確認してください。
- **移行先のミドルウェア導入** — クイックバーの「セットアップ」または`appwiz.cpl`からシナリオ定義のソフトウェアを導入します。APサーバーはJavaを先に導入してからResinをインストールします。DBサーバーはOracle導入後にサービスを起動し、`lsnrctl status`でListenerを確認してからData Pumpを実行します。
- **taskschd.msc** — 実行ファイル、スケジュール、実行ユーザーを確認し、移行したタスクを「試運転」して結果を記録します。自動起動設定とタスク試運転は運用品質と監査レポートに反映されます。
- **certlm.msc** — 個人・中間CA・信頼されたルートの証明書、有効期限、秘密鍵の比較・移行。
- **eventvwr.msc** — 切替後の状態に応じたイベントログから障害を調査。
- **notepad resin.conf / jdbc.properties** — 旧・新設定を比較し、編集・保存・移行。新APではresin.confの待受IPとDB接続先、jdbc.propertiesのDB接続先をそれぞれ新環境に合わせます。
- **JDBC移行** — APSV01でコピーを準備し、APSV02で受け取った後、`jdbc.url`を`DBSV02:1521:ORCL`に変更して保存します。コピーだけでは監査完了になりません。
- **切替前の疎通確認** — 新APで`curl http://APSV02:8080/`を実行します。Java／Resin、resin.confの待受IPとDB接続先、JDBC、DB Listener、必要な全スキーマを確認し、条件を満たすと`HTTP/1.1 200 OK`になります。
- **Oracleデータ移行** — 案件デスクの「DB移行方式」を選ぶと、DBサーバーの端末コマンドと監査要件が切り替わります。Data Pumpは現行DBで`expdp`、新DBで`impdp`を実行し、業務更新後に再実行して最終同期します。RMANは`rman backup`→`rman restore`でスナップショットを復元し、バックアップ後の更新があれば再バックアップ・リストアが必要です。Data Guardは`dgmgrl prepare`→新DBで`dgmgrl start standby`を実行し、以後の業務更新はデータ世代として自動同期されます。世代一致後に新DBで`dgmgrl switchover`を実行するとPrimary/Standbyの役割が入れ替わります。方式違い、Oracle未導入、サービス停止、未準備パッケージ、同期遅延はエラーまたは監査指摘になります。SQL*Plus画面の準備・適用ボタンも選択方式を使います。
- **dnsmgmt.msc** — DNSのAレコードとTTLを調査・切替。DNS適用は名前解決先の切替であり、疎通確認ではありません。シミュレーションではTTL短縮の適用で待機完了扱いにしますが、実環境では短縮後に旧TTLの満了を待つ場合があります。切替後は`ipconfig /flushdns`を実行し、`curl http://intra.example.local:8080/`で本番名経由の稼働を確認します。

「知識ノート」には実行した調査と確認理由が記録され、「仮説メモ」には調査中の考えを残せます。作業完了後は監査レポートを表示し、実施項目・見落とし・手順順序・移行成功率・推定停止時間・障害件数・復旧時間を確認できます。レビュー文と助言は現在ローカル規則で生成し、外部生成AIへは接続しません。

## 案件運営

セッション上部の「案件デスク」から、技術作業と並行して案件運営を記録できます。

- **案件概要** — シナリオ定義の利用者数、停止可能時間帯、許容停止時間、重要度を確認。
- **調査・構成** — 調査結果をノートへ記録し、接続元・接続先を入力して構成図を作成。シナリオの依存関係との一致は監査レポートで評価します。
- **計画・周知** — 停止時間、TTL短縮・利用者周知のリード日数、DB移行方式の計画、切戻し条件を記録。TTL短縮は切替3日前以上の計画とDNSマネージャーでの事前適用を別々に監査し、シミュレーション上の待機完了と実時間の経過は区別します。周知はシミュレーション内の送信記録で、メールは送信されません。
- **切替判断** — Go / No-Goを記録し、切替後は障害を許容して継続するか、DNSを現行APへ戻すかを選択。Go判断前に、新APへの疎通、選択したDB方式とデータ同期、DNS TTL、今回の利用者周知、停止時間、切戻し手順、未解決ログを一覧で確認できます。未完了項目はGo記録時にも通知されますが、判定やDNS操作を強制的にブロックしません。DNS TTLはAレコード変更前に単独で短縮・適用する必要があり、同時適用では旧キャッシュが残ります。切戻しでも権威DNSだけが戻り、クライアントキャッシュは自動更新しません。必要に応じて`ipconfig /flushdns`後、本番名でHTTP 200を確認します。切替後に再切替する場合、過去サイクルのGo判定・周知・疎通確認は引き継がれず、改めて記録・確認します。設定・サービス・DBを疎通確認後に変更した場合は、再度新APへの直接疎通を確認してください。
- **監査レポート** — 調査・設計・移行・障害対応・セキュリティ・運用品質を個別採点し、未実施の具体的な修正方法と総合評価を表示。Go / No-Go、事前疎通、利用者周知、DNS切替後のキャッシュ更新・本番名疎通が、最新の切替サイクルで適切な順序で実施されたかも確認します。最終状態が切戻しの場合は移行完了として扱いません。

DB移行コマンドは教育用の疑似操作です。各方式はスキーマとデータ世代で差分・同期状態を表現し、実際のOracle行データ、バックアップファイル、転送量、Oracle製品コマンドの全仕様はシミュレーションしません。

## シナリオ追加

`src/data/scenarios/*.json` の各JSONが案件です。起動時にJSONを自動検出するため、基本的にはファイル追加だけで案件選択に表示されます。Zodで構造と参照を実行時検証します。

シナリオには次を定義します。

- `project`: 利用者数、許容停止時間・停止枠、重要度、構成要素、監査評価に使う依存関係
- サーバー、VM、Database、DNS、サービス、タスク、証明書ストア、構成ファイル。移行先サーバーの`software`配列はセットアップで導入可能なミドルウェアを表します。
- 疑似コマンド出力と障害イベント
- エキスパートモードで抽選する障害は`requiredAsset`に`service`、`certificate`、`jdbc`、`task`のいずれかを指定し、対応する移行元資産も定義します。
- 難易度別の学習目標順序と実行後の解説
- チュートリアルの手順・完了イベント・解説
- 監査チェック、未実施操作の説明、修正方法、影響、重み、推奨作業順序

サーバーには`stage`（`source` / `target` / `infrastructure`）を指定します。学習目標の`commands`、監査項目の`requiredEvents`と操作イベント名は、画面のヒントやレポートと連動します。追加シナリオはIDの一意性、VMとホストの双方向参照、DB配置先ロール、DNSのIP参照、障害ごとの再現資産・修復操作、監査項目を網羅する推奨順序なども読み込み時に検証されます。検証は`npm test`でも各不正ケースを含めて確認できます。

`project.dependencies`は`id`、`from`、`to`、`reason`を持ち、`from`と`to`は`project.components`に定義します。プレイヤーが案件デスクで記録した依存関係と比較し、設計品質を採点します。

将来の生成AI連携用に`Advisor`インターフェースを定義しています。現在は外部サービスや資格情報を使いません。
